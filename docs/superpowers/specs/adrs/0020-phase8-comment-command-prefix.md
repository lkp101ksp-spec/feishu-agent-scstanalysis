# ADR-0020: 评论指令前缀约定（非 LLM 意图理解）

| 字段 | 值 |
|---|---|
| 状态 | 已批准（2026-08-26）|
| 决策者 | 用户 + Claude |
| 影响 Phase | Phase 8 |
| 相关 spec | §4 评论触发动作 |

---

## 背景

评论驱动闭环需要把"导师评论"翻译成 agent 动作。需决定解析机制。

---

## 选项

### A. 指令前缀约定（已选 ✅）

评论正文以 `/replan` `/revise` `/add-step` 开头 → 字符串前缀匹配 + 空白切参。

- **优点**：确定性强；AST/单元级可测试；零 token 成本；解析失败可精确报告
- **缺点**：用户需记指令语法；自然语言评论不触发

### B. LLM 全量意图理解

每条评论过 LLM 判断是否为动作 + 参数抽取。

- **优点**：自然语言友好
- **缺点**：不可控（幻觉动作）；测试困难；每条评论 token 成本；误触发风险高

### C. 仅 IM 通知不执行

评论只展示，动作仍在 IM 手动输入。

- **优点**：最安全
- **缺点**：闭环没闭上，评论与模板操作割裂

---

## 选择：**方案 A（指令前缀约定）**

指令语法：

| 指令 | 语法 | 语义 |
|---|---|---|
| `/replan <tid> <note>` | description 追加 `[replan by <user>] <note>` | version bump |
| `/revise <tid> <desc>` | description 覆盖 | version bump |
| `/add-step <tid> <tool>` | steps_json 追加一步（仅 subplan） | version bump |

解析规则：前缀不匹配 → 普通评论（跳过不打标）；参数不足 → 该条 failed，不中断批次。

---

## 后果

### 正面

- 解析纯函数化（parse(text) → ParsedAction | None），100% 可单测
- 与 IM 指令（/template-*）风格统一，用户心智一致
- 所有动作走 VersionService，版本可回滚

### 负面

- 指令语法写错不触发（需文档引导）
- 自然语言建议（"建议加个对照组"）不会被解析

### 中性

- LLM 辅助解析（前缀 miss 时的建议推荐）推迟 Phase 9

---

## 回滚条件

1. 用户普遍不会写指令语法（apply 使用率 < 10%）
2. Phase 9 若引入 LLM 解析，前缀模式保留为快速通道（混合模式）
