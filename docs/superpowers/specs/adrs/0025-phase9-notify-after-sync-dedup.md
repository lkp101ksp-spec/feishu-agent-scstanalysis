# ADR-0025: pending 推送在 sync 后即时触发 + notify 日志去重

| 字段 | 值 |
|---|---|
| 状态 | 已批准（2026-08-26）|
| 决策者 | 用户 + Claude |
| 影响 Phase | Phase 9 |
| 相关 spec | §4 pending 摘要推送 |

---

## 背景

自动同步落地后，owner 仍需主动查询才发现有待处理动作。需决定**何时推送**与**如何防轰炸**。

---

## 选项

### A. sync 后即时推送 + notify 日志表去重（已选 ✅）

每次自动 sync 后检测"新增待处理动作评论"（pending + parse_action 命中 + 未通知过）→ 非空则 IM 推送 owner（摘要 + apply 提示）→ 写 `comment_notify_log` 持久去重。

- **优点**：闭环延迟最短（= interval）；同一评论终身只通知一次；重启不重发；空集不发消息（零噪音）
- **缺点**：新增一张小表；手动 sync 路径不推送（需区分触发源）

### B. 每日定时汇总

每天固定时间汇总 pending 推送。

- **优点**：最安静
- **缺点**：延迟一天，评论闭环时效性丧失

### C. 仅 owner 主动查询（不做推送）

- **优点**：零改动
- **缺点**：自动同步的价值无法传导到人

---

## 选择：**方案 A（sync 后即时推送 + 去重）**

语义要点：

1. 触发源**仅** auto_sync_worker（手动 `/comments-sync` 不推送——owner 主动行为无需提醒）
2. 过滤：`processed_at IS NULL` + `parse_action(text) != None` + `not notify_log.has(cid)`
3. 消息含动作摘要（评论者 + 指令原文）与 `/comment-apply <doc_id>` 提示
4. 推送与打标同事务倾向（先 IM 后写日志；IM 失败不写日志 → 下轮重试）
5. apply 后评论离开 pending，天然不再命中（与 Phase 8 幂等链一致）

---

## 后果

### 正面

- "导师评论 → owner 被告知 → 一条指令应用"全链路自动化
- 去重持久化，重启安全
- 权限模型不变：apply 仍由 owner 显式发起（ADR-0023 不破坏）

### 负面

- `comment_notify_log` 表（16→17）
- IM 失败后下轮重试可能造成延迟到达（可接受）

### 中性

- 交互式卡片批量 approve / 日报模式推迟 Phase 10

---

## 回滚条件

1. owner 反馈推送频繁（动作评论密度高）→ 降级为每轮汇总单条消息（去重表不变）
2. IM 通道故障率 > 5% → 加推送失败退避
