# ADR-003: 上下文压缩双阈值策略

| 字段 | 值 |
|---|---|
| 状态 | 已批准（2026-08-09）|
| 决策者 | 用户 + Claude |
| 影响 Phase | Phase 3 |
| 相关 spec | §4 ContextCompressor |

---

## 背景

长会话（>200k token）需要压缩，否则超出 LLM 上下文窗口。两种阈值策略：

1. **单阈值**：达到 X% 即压缩（可能压缩后仍超限）
2. **双阈值**：先 X% 总结，超 95% 才冻结（分层）

---

## 选项

### A. 单阈值 70%/90%

- 70% 时总结；90% 时冻结
- 优点：阈值少，逻辑简单
- 缺点：总结后仍可能超 90%，需立即冻结，体验差

### B. 单阈值 80%

- 80% 时立即冻结
- 优点：决策简单
- 缺点：浪费 summary 机会（先用尽压缩再冻结更平滑）

### C. 双阈值 80% + 95%（已选）

- 80% 触发 LLM 总结
- 95% 触发 session 冻结
- 优点：总结 + 冻结分层；给 LLM 留 buffer；体验平滑
- 缺点：逻辑稍复杂；需实现 estimate_tokens 与 maybe_compress 两阶段

### D. 动态阈值

根据历史对话长度自适应阈值

- 优点：理论上最优
- 缺点：实现复杂；产品决策模糊

---

## 选择：**方案 C（双阈值 80% + 95%）**

---

## 后果

### 正面

- 总结 + 冻结分层；体验平滑
- 给 LLM 留 buffer（80% → 95% 还有 15% 空间）
- 与业界最佳实践一致（Anthropic / OpenAI 长会话策略）

### 负面

- estimate_tokens 调用增加（每次 LLM 调用前 +1 次）
- 阈值硬编码 → 需 settings 化（已加 settings.context_compress_trigger_ratio / context_freeze_trigger_ratio）

### 中性

- tiktoken 依赖（Phase 3 新增）；fallback 用 `len(text) // 4` 估算

---

## 回滚条件

1. 80% 触发太频繁（用户反馈"老是被压缩"）
2. 95% 触发太晚（实际超 LLM 窗口报错）
3. tiktoken 性能开销 > 5%

回滚方案：调整阈值（无需重写）；最坏情况切到单阈值 B。
