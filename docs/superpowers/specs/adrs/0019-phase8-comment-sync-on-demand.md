# ADR-0019: 评论按需增量同步（非 webhook、非实时）

| 字段 | 值 |
|---|---|
| 状态 | 已批准（2026-08-26）|
| 决策者 | 用户 + Claude |
| 影响 Phase | Phase 8 |
| 相关 spec | §3 评论持久化 |

---

## 背景

Phase 7 评论 fetch-only（ADR-015），重启即失且无法扫描"未处理评论"。Phase 8 需要评论落本地库，供动作触发与统计。需决定同步方式。

---

## 选项

### A. 手动/按需增量同步（已选 ✅）

`/comments-sync <doc_id>` 指令或 API 触发拉取；comment_id 幂等 upsert；root+reply 展平落库。

- **优点**：无公网回调要求（与现有 pull 模式一致）；部署零门槛；幂等可重放
- **缺点**：非实时（依赖用户主动同步）

### B. 飞书事件订阅 webhook 实时推送

comment 事件回调 → 实时落库。

- **优点**：实时；无需轮询
- **缺点**：需公网回调地址 + 事件验签 + 重试去重，部署门槛高

### C. 维持 fetch-only + 内存缓存

- **优点**：零改动
- **缺点**：重启丢失；无法做 pending 扫描，评论驱动闭环无法实现

---

## 选择：**方案 A（按需增量同步）**

关键语义：

1. comment_id 为幂等键（飞书侧生成，天然唯一）
2. 重复 sync 只更新 text / resolved / synced_at
3. **processed_at 不被 sync 覆盖**（防动作重放）
4. 飞书侧删除的评论本地保留（快照语义）

---

## 后果

### 正面

- 复用 Phase 7 CommentClient（含 rate_limiter），零外部依赖
- `/comment-apply` 有了稳定的 pending 数据源
- 评论历史可本地查询（stored API）

### 负面

- 新评论依赖用户手动 sync，无推送提醒
- 飞书侧删除不同步（快照与源可能漂移）

### 中性

- webhook 实时推送 / 评论分页 / tombstone 推迟 Phase 9

---

## 回滚条件

1. 用户反馈"必须实时"（≥ 30% 高频协作者）
2. 单 doc 评论量超 500 导致 sync 超时（此时加分页，不改架构）
