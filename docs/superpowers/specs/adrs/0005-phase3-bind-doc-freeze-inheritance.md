# ADR-005: bind_doc 冻结时是否继承

| 字段 | 值 |
|---|---|
| 状态 | 已批准（2026-08-09）|
| 决策者 | 用户 + Claude |
| 影响 Phase | Phase 3 |
| 相关 spec | §4.4 Session 冻结 / §1.3 关键约束 |

---

## 背景

Phase 3 引入 session 冻结：长会话超 95% 时，把旧 session 标 archived，开新 session。bind_doc 是 30 分钟一次性授权，冻结时新 session 是否继承？

---

## 选项

### A. 不继承

新 session 不带 bind_doc。用户必须重新 `/bind-doc <doc_id>`。

- 优点：最安全；用户明确知晓
- 缺点：体验差；每次冻结都要用户重授权

### B. 继承（已选）

新 session 继承原 bind_doc_id 与 bind_expires_at（如果未过期）。如果原 bind 已过期则不继承。

- 优点：用户零打扰；剩余有效期通常足以用完
- 缺点：可能"延长"了用户预期之外的授权

### C. 条件继承

仅当剩余有效期 > 1 小时时继承；否则不继承。

- 优点：避免快过期 bind 误用
- 缺点：阈值（1 小时）需决策；增加复杂度

---

## 选择：**方案 B（继承）**

---

## 后果

### 正面

- 用户零打扰（最常见情况：剩余 25 分钟冻结，仍可用 25 分钟）
- 实现简单（session 表加 origin_session_id 字段；新 session 查 origin 拿 bind）

### 负面

- 用户预期外的"延长"（用户以为 bind 已过期，实际未过期被继承）
- 没有强制重新授权的安全检查

### 中性

- 剩余有效期 < 0 时不继承（保留原行为）
- audit_logs 记录冻结时的 bind 状态

---

## 回滚条件

1. 用户反馈"我以为已经过期了，被自动续了"
2. 安全审计发现冻结被滥用（用户主动冻结以保留 bind）

回滚方案：切到方案 A（新 session 不带 bind），需修改 freeze_session 实现。
